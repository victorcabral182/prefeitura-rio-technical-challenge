# Diário de bordo

Registro cronológico e informal. Desenvolvido em par com Claude Code (ver declaração de IA no README).

## 2026-11-11

- Scaffold da API com `nest new`: veio NestJS 12, já ESM, com Vitest e oxlint (esperava CommonJS + Jest + ESLint). Imports relativos terminam em `.js`. Sigo o padrão do framework.
- Scaffold da UI com `create-vite`: Vite 8, React 19, TypeScript 7, oxlint.
- Monorepo sem npm workspaces: cada serviço tem o próprio lockfile e builda com a própria pasta como contexto. Com workspaces, todo build Docker precisaria do lockfile da raiz. Custo aceito: o contrato dos eventos vai ser duplicado entre api e worker.
- Worker em Node puro, sem Nest: é um consumidor de fila, sem rotas nem DI. O Node 24 roda `.ts` direto (type stripping), então não tem build e o `tsc` fica só para typecheck. Testei num `node:24-alpine` antes: roda sem warning.
- Dev 100% em Docker com `docker compose up --watch`: sincroniza `src/` para o container e rebuilda quando o `package.json` muda. Descartei bind mount por dois motivos: o `node_modules` em volume anônimo fica desatualizado e o `dist/` criado como root aparece no host. Medi o hot reload: ~1–1,6s na api, no worker e na ui.
- `.dockerignore` com `node_modules`: evita que o `COPY . .` leve para a imagem Alpine (musl) o `node_modules` do host (glibc), com binários nativos incompatíveis.
- **Mongo não subia** (exit 1): `MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility with this version of MongoDB` (SERVER-121912). Meu kernel é 7.0. Testei as imagens: a `mongo:8` (hoje 8.3.13) recusa até `mongod --version` e a `mongo:9` (9.0.4) sobe. Segundo o Jira, todo o 8.0+ é afetado: o TCMalloc viola a ABI do `rseq` e o kernel 6.19 expôs isso. Fui de `mongo:9`.
- Healthcheck do MySQL via TCP (`-h 127.0.0.1`): no primeiro boot o entrypoint sobe um servidor temporário com `--skip-networking` (conferi no `docker-entrypoint.sh`), e um ping por socket daria healthy antes da hora.
- RabbitMQ: o `guest` só conecta de localhost, então criei um usuário de dev. Hostname fixo porque os dados ficam no nome do nó (`rabbit@<hostname>`).
- **RabbitMQ a 46% de CPU parado** no `docker stats`. Amostrei de 2 em 2s: base de ~0,2% com picos de 172% a cada ~10s, que era o intervalo do healthcheck. O `rabbitmq-diagnostics` sobe uma VM Erlang a cada execução (~0,9s), e o `mongosh` também pesa (~0,6s). Mudei os healthchecks para checar a cada 2s no boot (`start_interval`) e a cada 30s depois. No compose o healthcheck só segura o `depends_on`. O boot do zero caiu de 12,3s para 9,8s, e esses picos não vão poluir o k6.
- Testei o tempo de parada dos containers (Node como PID 1 ignora SIGTERM sem handler): <0,4s nos três, porque o npm repassa o sinal. `init: true` não foi necessário.
- Credenciais saíram do compose para um `.env` fora do git, com `.env.example` de referência. Usei interpolação `${VAR:?defina no .env}` em vez de `env_file`: cada container recebe só as próprias variáveis e o compose falha com mensagem clara se faltar alguma. Como a branch ainda não tinha PR, reescrevi os commits para a senha não ficar no histórico (eram só de dev, mas preferi começar certo).
- Pegadinha do MySQL: ele só lê `MYSQL_*` na primeira inicialização. Com o volume antigo a senha continua a anterior; precisa de `docker compose down -v`.
- Revisei as decisões da etapa 1 uma a uma e registrei as duas de arquitetura (monorepo sem workspaces e worker sem Nest) no DECISIONS.md. PR #1 mergeado em `develop`.
- UI: diagramei login, listagem e criação de corrida sem API, com dados em memória e troca de tela por estado. Os forms usam as form actions do React 19 (`FormData`), sem um `useState` por campo.
- Login: a primeira versão era um campo para colar o JWT, lendo o "token estático pré-gerado" do enunciado ao pé da letra. Troquei para e-mail e senha. Consequência: a API vai precisar de um endpoint que emita o JWT; decidir na etapa da API.
- Alterei a UI e o container continuou com a versão antiga: o `compose watch` não estava rodando, e sem ele o container usa o código da imagem. Resolvi com `docker compose up -d --build ui`.
- Banco da API com Prisma (tenho mais vivência prática com ele) e migrations versionadas. Modelo: `usuarios` com `tipo` ENUM `passageiro`/`motorista` (mesmo vocabulário do enunciado e do perfil no JWT) e `corridas` com `passageiro_id`, `motorista_id` (preenchido ao aceitar) e os 4 status como ENUM. IDs em UUID v7, ordenado pelo tempo, para os inserts não espalharem páginas no índice clusterizado do InnoDB.
- Surpresa no npm: a tag `latest` do CLI `prisma` aponta para `8.0.0-rc.33`, enquanto o `@prisma/client` está em `7.10.1`. Fixei as três dependências em `7.10.1` com `--save-exact`.
- Prisma 7 mudou bastante: generator `prisma-client` com `output` obrigatório (gerei em `src/generated`, fora do git), URL do banco no `prisma.config.ts` e MySQL via driver adapter `@prisma/adapter-mariadb`. Configurei `moduleFormat = "esm"` e `importFileExtension = "js"` por causa do ESM com `nodenext` do Nest 12.
- Migrations aplicadas no start do container: `prisma migrate deploy && exec npm run start:dev`. O `exec` é para o npm receber o SIGTERM; medi o `docker compose stop api` em 0,39s. No restart aparece "No pending migrations to apply".
- O `migrate dev` precisa de um shadow database, e o usuário `corridas` só tinha acesso ao próprio banco. Gerei a migration inicial com `migrate diff --from-empty`, mas o CLI imprimiu "Loaded Prisma config" no stdout e a linha caiu dentro do `.sql`; tirei na mão. Depois resolvi de vez com um script em `mysql/initdb/` que dá `CREATE`/`DROP` e acesso aos bancos `prisma_migrate_shadow_db_*`, só no dev. Testei com um campo temporário: a migration foi gerada e o shadow database apagado no fim.
- A pegadinha do MySQL que eu mesmo anotei me pegou: a api deu `P1000: Authentication failed`. O container do MySQL foi recriado com as senhas do `.env`, mas o volume guardava as antigas. Recriei o volume, que estava vazio.
- "No migration found in prisma/migrations": a imagem foi buildada antes de eu criar a migration. Sem `--watch`, precisa rebuildar.
- Migration criada com `docker compose exec` ficaria só dentro do container, porque a api não tem bind mount. O fluxo documentado no README usa `docker compose run --rm` com `./api/prisma` montado e `--user` do host, para o arquivo não nascer como root.
